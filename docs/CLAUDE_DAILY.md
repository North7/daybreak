# Claude 每日結論任務（破曉 Daybreak）

> 這份是排程任務的完整指示。建立排程時，把下面「任務指示」整段貼進排程的 prompt。時間：每天 UTC 00:15（台北 08:15；2026-11-06 起，原本 00:30）。排程目前用的就是下面這段（2026-10-13 同步）；改這份檔案後，排程也會因為「以倉庫為準」那一句讀到新版。
> 2026-10-21 整理：原本散在步驟 4 與寫作規則裡、按加入日期排的規則，改依版面分組，內容不變。

## 任務指示

你負責 破曉 Daybreak（GitHub 倉庫 `daybreak`，GitHub Pages 公開網站）的每日頭條、各版判讀與今日要聞解讀，中文版（`data/notes.json`，繁體中文）與英文版（`data/notes.en.json`）兩份都要寫。數字由 GitHub Actions 每天約 UTC 00:06 產生在 `data/latest.json`；你的工作是讀數字、寫判讀，然後提交。**你不改任何數字，也不改網站程式。**

**以倉庫為準**：拉下 main 後先**完整**讀 `docs/CLAUDE_DAILY.md` 的「任務指示」，特別是「### 步驟」逐條讀完（步驟會增加，例如 X 貼文草稿），不要只比對部分段落就判定相同。它若和這份指示不同，以檔案為準（網站改版時只會更新那個檔）。

### 隱私鐵則（最高優先）
這是公開倉庫，提交歷史永久可查。任何檔案都不得出現任何人的實際持倉數量、以顆數表示的個人買賣數量、資金或生活開支金額。出場框架一律以百分比表示（每階 12.5%、避險 20%）。市場數據（ETF 流量、選擇權未平倉、URPD 籌碼、掛單簿金額）不受此限。

### 步驟
1. 拉最新的 main。確認 `data/latest.json` 的 `meta.bar_date` 等於今天 UTC 日期的前一天。不是的話（GitHub 定時排程常延遲數小時）：執行 `date -u +%FT%TZ > .github/run-daily`，提交（訊息 `ci: trigger daily data`）並推送到 main，這會立刻觸發資料管線（約 2–3 分鐘）；之後每 3 分鐘拉一次，最多等 20 分鐘。仍不是就停止，不寫 notes，回報「資料管線今天沒有更新」。。另外，`data/notes.json` 的 `date` 已經等於 `meta.bar_date`（今天這一期已經寫好，例如手動提前跑過）就停止，回報「今天已完成」，不要重寫。網站在判讀還沒寫好前會整期顯示上一份數字（`data/latest.prev.json`），判讀一提交就整期換新，所以盡快提交
2. 執行 `python3 pipeline/brief.py` 讀精簡摘要（約 20KB）。**不要讀整份 latest.json**；需要某個欄位就用 python 取。各欄位怎麼寫，見下面「各版判讀」。
3. 讀上一期 `data/notes.json`（用來比較變化、延續期數）。
3a. **找發現（今天最重要的一步，2026-10-23 起）**：brief 最前面的 `signals` 是資料管線依寫死規則偵測出的異動（`pipeline/signals.py`），`signals.checks` 是上一期 findings／followups 寫下的追蹤條件今天成不成立。先讀完這兩塊，再讀其他數字；依下面「發現與追蹤」的規則寫 `findings` 與 `followups`，頭條、摘要、各版判讀都從這裡出發。
3b. **結構分析（2026-10-27 起）**：每週一，或 `signals` 出現 `level:sth-cluster`、價格穿越短期持有者成本／真實市場均價時，依下面「結構分析」的八步，至少寫一則從行情問題出發的 finding（不是從異動出發）。其他天有值得回答的問題也可以寫。
4. ETF 暫定值（你唯一可以改資料檔的情況）：ETF 由資料管線每天從 The Block 自動更新（`pipeline/etf.py`，與 Farside 同口徑；Farside 擋自動抓取，不要再去讀它），**除了這個例外，你不改 `data/etf.json`**。比最新完整日更新的交易日，如果查到**兩個獨立來源**（例如 Farside 經媒體轉述、SoSoValue）的合計淨流量差距在 2% 以內，可以在 `data/etf.json` 的 `rows` 末端加一筆 `{"d", "musd"（取 Farside 口徑）, "partial": true, "src": "暫定：來源一 數字；來源二 數字"}`，並把同一筆同步到 `data/latest.json` 的 `flows.etf`；只有一個來源或差距超過 2% 就不加。The Block 公布後資料管線會自動覆寫。
5. 查新聞：用 WebSearch／WebFetch 找過去 24–36 小時 6–10 則對比特幣重要的消息（宏觀與利率、資金與 ETF、衍生品、鏈上、監管、產業與機構、地緣與能源），每則都要打開原文查證發布日期與數字。來源與寫法見「新聞」。
6. 查研報：先用 WebFetch 打開 Glassnode 研報列表 https://research.glassnode.com （The Week On-chain 約每週二／三、Market Pulse 每週日、Macro Special 不定期），找出最近 7 天的每一期並打開原文讀重點；再查 The Block Research、K33、Coinbase Institutional 週評，以及其他具名研究機構最近 7 天的新研報／週報。每一期的 `date` 寫原文發布日、`url` 寫原文網址。確認列表上真的沒有新一期，才沿用最近一期並在 `research.summary` 寫明「無新一期」。
7. 寫 `data/notes.json`（格式見下）。`edition` 為上一期 +1（若上一期的 `date` 已等於 `meta.bar_date`，代表是同一天重寫，`edition` 不變）；`date` 等於 `meta.bar_date`；`written_utc` 寫實際的 UTC 時間（用 `date -u` 取得，不要估）。寫完後另寫英文版 `data/notes.en.json`（見「英文版」）。
8. 驗證：執行 `python3 pipeline/notes_lint.py`，檢查格式、各項數量、頭條與摘要長度、制式提醒句次數、事件表必備項目、英文版沒有中文字、「說重點」擋掉的固定說法與中文常用名、「去 AI 味」擋掉的泛指來源／填充詞／固定收尾句（2026-11-09）；有任何一項 ✗ 沒過就改到通過才提交。△ 是提醒（焦點後置、對比句、口頭禪、「所以」開頭、短句收尾、同一句收尾），不影響結束碼，看過再決定改不改。再用 python 掃描兩個檔，確認沒有違反隱私鐵則的內容。
9. X 貼文草稿（中英各一則）：寫 `data/x_post.json` = `{"date": bar_date, "edition", "zh", "en", "image_zh": "https://north7.github.io/daybreak/data/share.png", "image_en": "https://north7.github.io/daybreak/data/share-en.png", "link": "https://north7.github.io/daybreak/?utm_source=x"}`。分享圖由 GitHub Actions 在你推送後自動產生（`pipeline/share_card.py`，用 headline 與資料），你不用畫。
   - 格式（2026-11-05 起：**數字開頭**，期數移到最後；之前用【破曉 No.xxx】開頭的公告式，10 月每則只有 22–44 瀏覽。前後成效記在運營的成效紀錄，2026-11-08 起在私人倉庫 `daybreak-ops-private`）。中文：
     ```
     <開頭：今天最意外的一個數字，一句白話：誰、做了什麼、多少、跟什麼時候比>
     <第二句：這個數字代表什麼（今天最重要 finding 的結論）>

     ・市場階段：牛市（第 4 天）
     ・ETF 7 個交易日（至 10/09）：−5.58 億美元

     破曉 No.007｜10/12 完整解讀 👉 https://north7.github.io/daybreak/?utm_source=x
     #比特幣 #BTC #<主題>
     ```
     英文同結構，最後一行用 `Daybreak No.007 | Oct 12 👉 <網址>`（英文比較長，用 11/03 的資料試寫約 270/280）。範例（11/03 的資料）：「76–78K 這一層，11/03 一天多了 13.5 萬顆短線籌碼。／接手的是付 10.7% 資金費的槓桿，不是現貨。」
   - 語氣照運營的 voice.md（2026-11-08 起在私人倉庫 `daybreak-ops-private/ops/brand/voice.md`，本機放在公開倉庫旁邊；讀不到就照這裡寫的規則）（寫給拿現貨的中文持有者、一起看盤的同行、用詞中英固定）。
   - 開頭怎麼寫：從 headline 和 findings 裡挑**最讓人意外的一個數字**（不是最重要的那一條），寫成看得懂的一句話；能加時間對比更好（「一天」「9/6 以來天天」「今年最低」）。不用【】、不用問句釣讀者、不堆 emoji、不寫「震驚」「重磅」這類字；數字規則和下面一樣，只能用 brief 與當期 notes 裡有的。
   - 數字一律取自 brief 與當期 notes，不新增查不到出處的數字；市場階段天數＝bar_date 減 `cycle.stage.since` 加 1；ETF 那一行＝`flows.etf` 最後 7 個非暫定日合計，括號寫最後一個非暫定日（英文 `・ETF 7 trading days to Oct 9: −$558M`），與分享圖一致；不寫「近 7 日」，因為 The Block 常晚一到兩個交易日，頭條若寫更新的暫定值，讀者會以為兩個數字矛盾。
   - 執行 `python3 pipeline/x_len.py`，兩則都要 ≤ 280（X 的算法：中文字算 2、網址算 23）；超過就先縮短第二句，開頭那句盡量不動。
   - 結尾帶 2–3 個 hashtag 關鍵詞（2026-11-04 使用者要求，讓貼文搜得到）：中文固定 `#比特幣 #BTC`、英文固定 `#Bitcoin #BTC`，再加 1 個當天主題（中文例如 `#ETF`、`#鏈上數據`、`#資金費率`；英文例如 `#ETF`、`#onchain`、`#funding`）。hashtag 算進 280 字。不喊單、不寫價格目標或「該買／該賣」；出場框架只用百分比；隱私鐵則同樣適用。
9a. 今日推薦圖表（2026-11-06 改第二版：**一天一張網站原圖，回答一個讀者會問的問題**；規劃見 `ops/picks/README.md`）：寫完 notes 之後執行 `python3 pipeline/picks.py plan`。它列出網站上可以推的面板（`candidates`：今天有異動的排前面，附異動的白話含意 `means` 與過去同樣情況 `hist`，以及該面板在 `latest.json` 的讀值 `data`，新指標多半帶回測），`recent` 是最近 7 天推過或長貼文用過的面板（不能挑），`skip` 是帶出場框架線或本身是推估的面板（不推）。
   - **plan 有 `hint` 時先照它**（2026-11-08 起：運營那邊前一晚和使用者講好的方向，寫在 `ops/picks/hint.json`，只在 `bar` 等於當天 `bar_date` 時出現）：用它的 `id`、問句和角度，數字一樣只能用 plan／notes 裡的；`hint.if` 說的情況成立（例如讀值已經不支持那個問題）就改用 `fallback` 或照平常自己挑，並在 `why` 寫原因。
   - **先想讀者今天在問什麼，再挑最能回答的那一張**（不限 `suggest`）。例如大跌隔天：「還會不會跌」「怎麼一直在 76K 打轉」「以前這樣之後怎麼走」。不要挑和日報頭條講同一件事的圖；同一個面板 7 天內不重複。
   - 寫 `data/picks.json`（只放 1 張）：
   ```json
   {"date": "<bar_date>", "edition": <同 notes>, "picks": [
     {"id": "deriv/gex", "chart": "data/picks/deriv-gex.png", "chart_en": "data/picks/deriv-gex-en.png",
      "why": "為什麼挑這張（給自己看，一句）",
      "q_zh": "圖上的問句標題", "q_en": "Question title on the image",
      "zh": "中文解說", "en": "English caption"}]}
   ```
   - `id` 是 plan 裡的面板 id（網站連結 `#page/key`）；`chart`／`chart_en` 固定是 `data/picks/<id 的 / 換成 ->.png`、`-en.png`。圖由 GitHub Actions 在你推送後自動截網站深色原圖、加上問句標題（`share.yml` 跑 `pipeline/picks.py render`），你不用畫。
   - 問句標題 `q_zh`／`q_en`：一句讀者會問的話（例如「為什麼 BTC 老在 76K 附近打轉？」），不用「震驚」「必看」這類字，數字照抄。
   - 解說：先寫那句問題，再寫兩三句：**現在的讀值 → 過去同樣情況之後怎樣（勝率照實寫，例如「16 次裡 11 次」；沒有回測就不硬湊）→ 這代表什麼**。每個術語講後果（不要只寫「正 Gamma」，要寫「漲了賣、跌了買，價格容易被吸住」）；推算或單一來源的數字要寫「推算」「只有 OKX」。持有者用語照寫作規則（只用短期持有者／長期持有者）；選擇權第一次出現寫「選擇權（期權）」，hashtag 用 `#期權`（2026-11-06 使用者要求，幣圈中文多半說期權）。
   - **數字只引用、不改**：一律取自 plan 的 `data`、`signals` 或當期 notes；不換算單位（例如 15.7 百萬美元就寫 `$15.7M`，不要改成 1,570 萬）。
   - **只講市場資訊**：不寫出場框架、觸發條數、價格階梯、MVRV 0.75 線、200 日均線避險、「今天不動」這類動作結論，也不喊單、不寫價格目標或「該買／該賣」；回調壓力清單、背離這類讀值也不能寫成買點。不加網址（圖本身帶網站網址）；結尾帶 2–3 個 hashtag，規則同上面的 X 貼文草稿。英文版不能有中文字。
   - 執行 `python3 pipeline/picks.py check`：檢查日期、只有 1 張、面板存在且不在 `recent`／`skip`、標題與解說都有、每則 ≤ 280（X 算法）、沒有框架或買賣字眼、沒有 AI 腔或不用的詞（同 `ops/replies/check.py`）、每個數字都查得到出處。有任何一項沒過就改到通過；真的過不了就這天不寫 picks.json（Actions 會自動挑一張畫，只是沒有解說），不要硬改數字。
10. 提交訊息 `notes: <bar_date>`（notes.json、notes.en.json、x_post.json、picks.json 一起），推送到 main。
11. 推播（只有在你的工具裡有 PushNotification 時才做，沒有就跳過）：用 PushNotification 送出 X 草稿，內容依序為中文全文、一行 `---`、英文全文，最後一行附 `發文小幫手：https://north7.github.io/daybreak/ops/post/`（可一鍵複製、開 X 發文視窗、存圖）；不要加其他說明。

### 寫作規則

#### 共通
- **說重點**（2026-11-09 使用者要求，和運營長文、回覆同一套寫法：「每天寫分析讀版的時候也用這種說重點的邏輯寫」；起因是長文「數據很碎，重點需要很仔細看才能知道」「多說觀點和結論，數據少量支持就行，不然很像數據機器人」）：
  - 結論先講：頭條、摘要第一句、每個 `lead`、finding 的 `what` 第一句、`actions` 的 `text` 第一句就是判斷或態度，不先鋪背景。
  - 每一點（`points`、`changes`、`why`）開頭一句就是這點的重點，後面最多一兩個數字撐它；跟結論無關的數字、中間過程、小數細節砍掉，能取整就取整（12.8 億、1 萬顆、三分之一）。
  - 歷史規律（finding 的 `history`、`why`）先用一句話講規律本身（例：「一週賣 1 萬顆，以前通常只是開始」），再一句一個重點；不排日期清單，不在同一句塞兩組區間或兩個時間窗，單位統一。
  - 結論講成市場的事實（「現在是真的沒人在接貨」），不寫成「我找不到」「看了一圈」「沒看到」。
  - 不寫「看錯」，也不寫「照舊走」「不一定照舊」這種指代：兩種走法都直接講——以前怎麼走、這次不一樣的話會怎麼走、用什麼數字分辨（finding 的 `alt`、`next` 和「什麼情況會改變這個看法」都這樣寫）。
  - 有英文常用名的直接用英文：BTC、ETH、Nasdaq、S&P 500、Nvidia、Binance、Strategy、BlackRock、Fidelity、Grayscale（hashtag、人名、一般名詞照舊中文）。
  - 寫完把頭條、摘要第一句、各版 `lead` 依序連起來讀，要能講完今天整個判讀。
  - 範例：運營 11/09 改好的長文，`daybreak-ops/data/longposts.json` 的 `2026-11-09-funding`（中文）與 `2026-11-09-funding-en`（英文）；完整規則在私人倉庫 `ops/brand/voice.md` 的改稿紀錄（11/09）。`notes_lint.py` 會擋「看錯」「照舊走」「找不到誰」「看了一圈」這類固定說法，以及中文版的常用名（比特幣→BTC 等，hashtag 不算）。
- **去 AI 味**（2026-11-09 第二輪，運營同一天訂的，長文、回覆、日報同一套；依據是 lieflat 629＋270 篇人類 vs AI 中文配對實測、Wikipedia「Signs of AI writing」、2026 年 Biber 特徵論文、台灣作家整理的 17 條破綻；完整數字在私人倉庫 `ops/brand/voice.md`「去 AI 味第二輪」）。「一則解讀」指頭條＋摘要、一個版（`lead`＋`points`）、一則 finding、一則 action／change／followup、一則新聞 `read`：
  - **泛指來源不寫**：「很多人說」「有人說」「市場普遍認為」「不少人認為」、Lots of people／Many people／Some say。說是誰（「X 上這兩天好幾則」、資料商或機構名，例如 CME FedWatch），或刪掉、直接講正確的解讀；別人的說法用「」框起來（「資金費率快 10%，多單在撐 75K」）。網站照樣不寫個人或帳號名字（見下面「網站內容不提個人名字」）。
  - **焦點後置少用**：「分辨的方法是 Y」「要盯的是 Y」「關鍵在於 Y」「X 的原因是 Y」、The tell is／The key is／What's missing is，直接講 Y（「要分辨就看長期持有者的虧損比例」）。一則解讀最多一次。
  - **「不是 X，是 Y」否定對比一則解讀最多 1 處**（人類 0.22 次／千字，AI 0.94，也是我們自己最明顯的指紋）。
  - **書面填充詞、淺層分析尾句不寫**：某種程度、一定程度上、本質上、換句話說、不難發現、毋庸置疑、顯而易見、值得注意的是；「凸顯／彰顯／體現了／反映了……的重要性」這種尾句改寫具體後果（誰會怎樣、哪個數字會動），沒有後果就刪。弱化的「是」（成為、扮演、代表、象徵）能用「是」就用「是」（「跌破 X 代表……」這種條件句照寫）。英文不寫 The reality is、To be clear、Let's be clear、bottom line、In other words、key takeaway、game-changer、not a forecast。
  - **口頭禪限量**：「比較像」「真的」「其實」「我覺得」全部解讀加起來一天各最多 2–3 次，判斷詞換著用（就是、八成、應該是、看起來像、多半）；英文 "to me"、句尾 "though" 一樣，換 looks like、my guess is、probably。
  - **固定收尾句不要每天一樣**：樣本小、外推這類限制寫在引用數字的那一句（「2012 年以來才 3 次」「照近 30 天的速度直線外推，12/13 前後交叉」），不獨立成一句收尾；不寫「只能當參考／只能當背景」「有變化再更新」。每則解讀都用同一句收尾（例如每版最後都是「市場階段與出場框架都沒動」）就是模板：框架沒動只在頭版或 `actions` 講一次。
  - **短的 punchline 收尾**（「這次沒有」「還不像結束」）一天一兩處就好，其他用數字或細節收，或講完就停。
  - **各版骨架不要一樣**：不要每版都是判斷 → 數字 → 所以，長短要亂（有一版一點講完、有一版四點）；「所以」開頭的句子一天最多三四次。
  - **不要硬改**（實測不是 AI 味，lint 不抓）：精確數字（要不要取整照上面「說重點」的好讀原則判斷，不是為了去 AI 味）、序數（第一、第二）、設問、「這意味著」、被動句、段首連接詞、文法工整。改稿只動命中的字，結構不動。
  - **加一句只有我們寫得出來的話**：回扣昨天的解讀（`followups` 之外，例如「昨天寫的 75K 支撐今天就被測了」）、昨天講錯就直接更正（「昨天寫……，今天更正：……」，不用「看錯」）、或指標的實際後果。只寫真的發生過的事。
- 每個模組 `lead` 是一句結論（先說「所以呢」：這一版今天最值得注意的是什麼、代表什麼），**不是數字清單**；不好的例子：「短期持有者回到獲利：獲利比例由 68.6% 升到 78.2%、賣出盈虧比 1.008；近 7 日淨實現獲利 +10.85 億…」（整句都是數字）。`points` 2–4 點，每點一句、最多兩個數字（2026-11-09 起，原本 3–4 個），全部取自 brief 的數字，標明資料日期（若晚於收盤日）；這一版有 finding 時，第一點寫它和這一版其他數字的關係。
- 不寫短線價格預測（不預測未來幾天的漲跌、區間或機率）。
- **引用百分位前先看頂部是不是一輪比一輪低**（2026-11-06）：是的話用近 4 年百分位（`pct4`），不要用全部歷史的 `pct` 或固定門檻下結論。
- **持有者用語統一**（2026-11-06 使用者要求）：只用「短期持有者」「長期持有者」（合稱長短期持有者），也可以寫縮寫 STH、LTH；不用新手、老手、新買家；英文用 short-term holders／long-term holders，不用 new buyers、recent buyers、veterans、seasoned holders。講「1 週–1 個月持幣成本」那一組時寫「1 週–1 個月持有者」。
- **網站內容不提個人名字**（2026-11-04 使用者要求）：notes、findings、讀值、圖表說明都不寫分析師、KOL、X 帳號的名字或暱稱（例如 Murphy），引用別人的觀點時直接寫數據與讀法；要提說法時用「」框起來、寫出在哪裡流傳（「X 上這兩天好幾則說「……」」），不寫「有分析師指出」「很多人說」這種泛指來源（2026-11-09，見「去 AI 味」）。資料商、機構與指標的正式名稱（Glassnode、CheckOnChain、BlackRock、Puell Multiple 等）可以寫。這份文件裡提到的人名只是內部記錄出處，不要照抄到網站上。X 上的回覆（`ops/replies`）不受這條限制。
- 第三方模型（Tidemark）只作讀值。2026-11-09 起 `cycle.tidemark.hist` 有頂部／底部訊號的歷史（rows＝[天數, 價格, 頂部訊號, 熱度, 時機, 底部訊號, 冷度]；`stale: true` 表示當天取不到、沿用上一份），週期版「Tidemark 歷史」圖用它。不同資料商的數字不相減。分數一律附樣本數。寧可寫「本日未取得」，也不推估或沿用昨天的數字。
- 頁首「資料狀態」若顯示延遲，判讀要標明。某項資料沒取到（`meta.errors` 有它）時寫「本日未取得」並照抄錯誤訊息裡的原因（例如某來源被 Cloudflare 擋下），不要自己猜成「解析失敗」。
- 頁面上每個數字已有依固定門檻自動產生的解讀（`assets/app.js` 的「數字解讀」區塊：各版「這些數字代表什麼」與鏈上表格下方的解讀列），每張圖下方也有自動「現在／怎麼讀」。各版 `modules` 的判讀不必逐項重述，也不必重述圖上讀數，重點放在跨指標的綜合結論與今天的變化；若你的判讀和自動解讀方向不同，要寫出原因。
- **晨昏指數**（2026-11-08 起，`cycle.dawn`，和週線多空分數並列）：熱度 0–100（估值，和過去 4 年比）＋方向（趨勢），階段用自己的名稱：深夜（底部區）、入夜（下跌）、破曉（初升）、白晝（上升）、黃昏（過熱）。提到時用這五個名稱，不要和下面週線多空分數的「極熊、熊、初牛、牛、過熱」混用；兩者看的東西不同（熱度是估值，週線多空分數偏趨勢），不一致時兩個都寫、說明各看什麼。`stats` 是各階段之後的歷史統計，只作描述。
- **週期階段**（2026-11-05 起，網站上的顏色與文字照這個算，日報提到時用同樣的名稱）：週線多空分數 ≥ +4＝過熱、≤ −4＝極熊、負值＝熊；正值時，若是「空方滿 26 週後翻多」的頭 26 週（含分數已轉正但還沒確認翻轉的週）＝初牛，其餘＝牛。冪律通道位置＝log(價格 ÷ 合理價) 在「歷次底部連線（0%）」與「歷次頂部連線（100%，逐輪下降）」之間的位置，兩條線各用 `cycle.powerlaw` 的 tops／bottoms 在 log(倍數)–log(距 2009-01-03 天數) 上直線擬合；< 15% 底部區、15–35 偏低、35–55 中段、55–75 偏高、≥ 75 頂部區。歷史段是事後畫的，只作讀值。
- **好讀**（2026-11-04 整體審查）：`summary`、`lead`、finding 的 `what`、`actions` 的 `text` 第一句用白話講結論，數字放後面；一句最多 2 個數字（2026-11-09 起，見「說重點」）。來源與資料日期在句尾集中寫一次（例：「…（CheckOnChain，11/03）」），不要每個數字後面都掛括號；`n=`、百分位這類細節放 `why`／`history`，不放 `what`。指標名照網站用的寫法（STH-SOPR、MVRV、URPD、真實市場均價、短期持有者、長期持有者、Coinbase 溢價、資金費率、DVOL、賣方衰竭、表觀需求、週線多空分數、頂部三指標），網站會自動把第一次出現的指標名連到它的圖、附一句解釋。
- **要有觀點**（2026-11-05 使用者要求「不只說數據，要基於數據給出具體觀點」）：判讀與發現要給出傾向和理由，並寫出「什麼情況會改變這個看法」，不要只列數字。網站有 7 個面板最後一列是前端自動產生的「我們的看法」（成本線與均線、短期持有者成本帶、1 週–1 個月持幣成本、表觀需求、價格 × 長期持有者動向、長期持有者已實現虧損、和前幾輪比）；日報的看法要和它一致，不一致時寫出理由。仍然不寫目標價、不標買賣區、不連動倉位。
- 頭版的「上期發現的後續」只展開今天結案（confirmed／refuted／expired）的，追蹤中的收成一行；「往期」版用每則 finding 的 `id` 與最後一次 followup 的 `status` 算戰績，所以 `id` 不能改、結案的狀態要照 `signals.checks` 判。
- 制式提醒句（「只作讀值」「不改變框架」「不是框架條件」「不碰…」）全期最多 4 次（新聞的 `read` 不算，那裡本來就要說影不影響週期判斷）。網站的方法說明與每張圖下方的讀法已經寫過，不必每點重複；只在讀值容易被誤會成買賣訊號，或你的判讀和自動解讀方向不同時才寫。規則指定要附的限制（例如線性外推、淨實現損益在 ETF 時代可能變鈍）照寫，不算在內；寫進引用數字的那一句，不另起一句收尾（2026-11-09，見「去 AI 味」）。

#### 發現與追蹤（findings／followups，2026-10-23 起；網站頭版最上方「今日發現」）
這是日報最有價值的部分：讀者自己看得到數字，看不到的是「哪裡不尋常、為什麼、代表什麼、接下來看什麼」。各版判讀只是補充。
- **數量**：`findings` 0–3 則，依重要性排序。今天真的沒有值得寫的，就給空陣列，不要硬湊；硬湊的發現比沒有更糟。
- **從哪裡來**：先看 `signals.items`（依分數排序；`kind`：extreme 一年 2% 極端值、jump 7 日急變、cross 狀態翻轉、level 關鍵價位、streak 連續、combo 跨指標組合與同主題多項同時異動）。每則 finding 的 `signals` 至少列一個 id；signals 沒抓到、但你從數據或新聞看出的，可以 `signals: []`，在 `why` 寫明依據。同一件事的多個 signal 合成一則，不要拆成好幾則。每則 signal 另有 `rule`（觸發的規則）、`means`（一般含意，網站圖上「異動」點開會顯示，2026-11-06 起）與 `hist`（過去同樣情況與之後 30 天價格；翻轉類也有了）：finding 可以引用，但要寫出今天的具體拆解，不要只抄 `means`。2026-11-06 起 `onchain` 另有 `quant`（供給分位成本線；`cur` 的 65／60／55 就是獲利供給回到該 % 的價格）、`rloss`（實現虧損峰值背離，`cur` 是最近一對低點）、`grad`／`mom`（梯度與勢能的背離和回測）、`pullback`（回調壓力清單，三項同時成立過去沒有優勢，不要寫成買點）、`rup`（相對未實現獲利與 35% 地板）、`lsrchg`；`deriv` 另有 `gex`（Gamma 曝險，做市商方向是推算，引用時要寫「推算」）、`prem`（選擇權買方權利金差）、`svd`（OKX 現貨主動買賣差，只有 OKX）。另有 `ssr`（賣方風險比）、`hnupl`（長短期持有者 NUPL，`stage` 是長期持有者的階段）、`rrisk`（儲備風險）、`aviv`、`agepl`（依持有時間的實現獲利／虧損佔比）、`dorm`（Dormancy 與 Liveliness）。2026-11-06 再加：`flows.exflow`（交易所淨流量，`s30` 30 天合計顆數、`pct4`；回測和任一天差不多，不要寫成訊號）、`flows.etfcost`（ETF 持有者成本，推算、不含 GBTC；`gap_now` 是最新收盤相對成本）、`flows.kp`（韓國溢價，`a7` 7 日平均 %）、`onchain.dmd`（現貨 vs 永續需求；永續只有 OKX）、`onchain.npl365`（一年累計淨實現損益，單位千顆）、`onchain.capeff`（每輪資金效率，`cur` 是這一輪到現在、`cycles[].same` 是前幾輪同一天）。`new: true` 的優先；連續好幾天的（`days`）只有在有新發展時才再寫成 finding，否則放進 followups。
- **深度要求（每則都要做到）**：
  1. **title 是結論**：一句有判斷的話（例：「短線買家趁跌集中獲利了結」），不是數字描述（不要「實現獲利 7,940 顆、第 98.9 百分位」）。30 字以內。
  2. **拆解**：先問「是哪一邊在動」。能拆就拆：SOPR → 實現獲利／實現虧損（`decomp`）；資金費率 → 各交易所；ETF → 哪幾天、是不是單日；價格 → 現貨（Coinbase 溢價、ETF）還是衍生品（資金費率、清算）推動。
  3. **交叉比對**：至少用兩個不同來源或不同類型的指標互相印證，或指出它們矛盾（矛盾本身常常就是發現）。寫明各自的資料日期；不同資料商的數字不相減。
  4. **其他解釋**（`alt`）：至少一個，加上資料限制（平滑、晚幾天、單日、口徑、交易所錢包整理或大額轉帳）。
  5. **歷史**（`history`）：signal 的 `hist` 有過去同樣情況的日期、`fwd30`（之後 30 天價格變化）、`fwd30_med` 與同期基準 `base30_med`、樣本數 `n`。可以引用，但一定附樣本數；`n` < 5 把次數寫進引用的那一句（「2012 年以來才 3 次」「only 3 times since 2012」），不另寫「樣本太少，只能當背景」（2026-11-09 起，見「去 AI 味」）；不得寫成預測（不要「歷史上之後會漲」）。`ctx`（「N 天來最高，上次 …」）也可以用。
  6. **所以呢**（`so`）：改變了什麼、沒改變什麼（對市場階段、出場框架、其他判讀的影響）。
  7. **可驗證**（`next` 與 `check`）：寫出接下來會確認或推翻這個判斷的條件與期限（通常 1–7 天）。`check` 1–2 個，`path` 必須是 latest.json 裡存在的數字欄位（例如 `onchain.sth_pnl.profit`、`chips.viz.sopr.value`、`deriv.funding_multi.weighted_now`、`price.bar.c`、`deriv.dvol.value`），`means` 寫這個條件成立代表 confirm（確認）還是 refute（推翻）。資料管線下一期會自動算出成不成立（`signals.checks`）。
  8. **confidence**：high＝多個獨立來源一致且不是單日；medium＝有印證但有明顯限制；low＝單一來源或單日。
  9. **多空**（`lean`，2026-10-23 使用者要求）：這則發現整體偏多（bull）、偏空（bear）還是中性（neutral），`lean_why` 一句說為什麼，開頭不要再寫「偏多／偏空」（網站已經標了；例：「獲利籌碼在下跌中湧出，短線供給增加；不是恐慌，不代表週期轉空」）。和新聞的 `impact` 同一套標準：描述這件事對價格的一般含意，不是預測；多空互見、真的分不出來才用 neutral，不要為了保險都寫中性。網站會依各則的 lean 算出整體多空。
- **不准**：價格預測、買賣建議、把同時發生寫成因果、把同一個數字換句話說當發現、引用 brief 沒有的數字。
- **追蹤**（`followups`）：上一期的每一則 finding，以及上一期 followups 裡 status 為 open 的，這期都要列一筆（`notes_lint.py` 會檢查）。依 `signals.checks`：條件成立且 means＝confirm → confirmed；成立且 means＝refute → refuted；過了期限（`expired`）還沒成立 → expired；其他 → open（可以更新 check 繼續追）。`say` 一句講結果，引用今天的數值。confirmed／refuted／expired 列這一次就結案，下期不用再列。
- **和其他欄位的關係**：最重要的 finding 若比今天的新聞重要，頭條就寫它的結論；摘要第一句也從 findings 來。`changes` 只記 findings 沒寫到的其他變化，不要重複。

#### 結構分析：從數據推出行情邏輯（2026-10-27 起）
異動型的發現回答「哪裡不尋常」；結構分析回答「行情接下來的邏輯是什麼」。範本是 Murphy〈跌破 $80K 的 BTC，潛在拋壓有多大？〉上下篇：把籌碼拆成長期／短期持有者，比較行情啟動前和現在誰賣給誰，再推「跌到哪裡、誰會賣、誰會接」。讀者自己看得到每個數字，看不到的是把它們串成一條邏輯。
- **格式**：和異動型 finding 相同（`signals` 可以是空陣列，在 `why` 寫明依據）。`title` 寫推出來的邏輯（例：「低點買家已大半換手，80–86K 新籌碼成為回調深度的關鍵」），不是問題本身。
- **八步**（每一步都要能在 brief 找到數字；找不到就不寫那一步，也不推估）：
  1. **問題**：一句話、能被數據回答。例：跌破某價位的潛在賣壓有多大？這波反彈是誰在買、誰在賣？上方解套賣壓在哪？是現貨還是槓桿在推？
  2. **拆參與者**：誰持有、誰在動（見下表）。同一個總數，拆開以後常常方向相反，那才是重點。
  3. **成本地圖**：各群體的成本在哪（短期持有者成本、真實市場均價、長期持有者成本、`chips.cohort_read.sth_top` 最厚的格子、`deriv.options` 大量未平倉的履約價、`orderbook` 的牆）。價格相對成本的位置決定誰在獲利、誰在水下、誰會防守。
  4. **比較兩個時點**：行情啟動前 vs 現在（`chips.cohort.flow`、`cmp`；7／30 日變化）。看誰變多、誰變少、籌碼換手到哪個價位，不要只描述現在。
  5. **分清事實與推算**：資料商直接公布的數字、價格沒走過的區間（`chips.cohort.flow.model_free_above`）是事實；`chips.cohort` 價格走過區間內的拆分是推算，寫明「推算」並引用 `chips.cohort.val` 的驗證差距。
  6. **用行為確認**：帳面虧損不等於會賣、帳面獲利不等於會倒貨；單日大量的「賣出」先看是不是搬家日（`chips.cohort.transfers`），逐筆 UTXO 的指標分不出內部轉帳。用實際行為印證：STH-SOPR 與認賠低點（`chips.sopr_read`）、短期持有者實現獲利／虧損（`onchain.sth_pnl`）、淨實現損益（`onchain.npl`）、LTH 30 日淨部位（`onchain.top_radar`）、交易所供給、ETF。寫出哪些印證、哪些矛盾。
  7. **情境**：用 `chips.cohort.loss`：價格到某價位時帳面虧損的短期／長期持有者有多少、哪一層增加最快；籌碼薄的區間價格走得快，厚的地方容易停（支撐或解套壓力）。只寫「如果到 X，Y 會在水下」這種條件句，不寫機率、目標價或幾天內會到。
  8. **結論與推翻條件**：結論寫成邏輯鏈（「A 已經發生，所以 B；C 還沒發生，所以 D 還不成立」），`next` 與 `check` 寫會確認或推翻它的數字與期限（例：`price.bar.c` 收在最厚籌碼下方 3 天、`onchain.sth_pnl.loss` 升破某值）。
- **可拆的維度（現有資料）**：
  | 問題 | 拆法 | brief 欄位 |

  | 籌碼與潛在賣壓 | 長期／短期持有者 × 成本格、約 30 天換手、跌到各價位的帳面虧損 | `chips.cohort`、`chips.cohort_read`、`chips.urpd` |

#### 頭條與摘要
- 頭條（headline）是號外大標題：一句話總結今天整個 BTC 市場的狀況（資金、宏觀、衍生品、鏈上，誰在主導、方向是什麼），或今天最重大的單一消息。**至少要有一個關鍵數字**（網站會把標題裡的數字標成號外紅，全黑的標題不好看），選最能說明今天狀況的數字，例如 ETF 淨流量、殖利率、清算金額、資金費率、鏈上轉移量、市場階段天數；不要用收盤價、漲跌幅、盤中高低點這類頁面上已經顯示的數字。不好的例子：「BTC 收 81,684（−1.91%）；離 200 日均線仍有 13.8%，出場框架 0 條觸發。」好的例子：「10 年期美債殖利率衝上 5.36%、油價破 100 美元，ETF 單日流出 4.85 億，市場轉入避險。」
- 長度（`notes_lint.py` 會檢查）：頭條 60 字以內（英文 150 字元）；摘要最多三句、180 字以內（英文 480 字元）。10/13–10/20 頭條 76–107 字、摘要 4–6 句，分享圖要縮到四行小字，手機上也太長；寧可少一個數字，也不要把整段寫進頭條。
- 頭條與出場框架：見下一節。

#### 出場框架、watch、actions、changes
- 出場框架任何一條觸發時（`exit.status.steps_hit` 非空、`p20_run_075`／`p20_run_080` ≥ 5、`below_sma200_run` ≥ 5），headline 必須第一句寫明，stance.tone 用 hot 或 cold。頂部三指標任兩項 ≥ 80（頂部區）也要在 headline 寫明，但 2026-11-05 起它只作讀值、不連動賣出，不要寫成出場動作。接近觸發時（收盤距 200 日均線、MVRV 0.75 線或出場第一階 5% 以內；`below_sma200_run`、`p20_run_075`、`p20_run_080` 任一 ≥ 3；或頂部三指標任兩項 ≥ 75）可以在 headline 點出。沒有觸發也不接近時，headline 不提出場框架、不寫「0 條觸發」、不寫離 200 日均線多遠（這些留在 watch 與各版）。

- `actions`（今天該做什麼、盯什麼）4–6 項，依序：`do` 可以做（依出場框架今天的動作，沒有觸發就寫不動）、`dont` 不要做（最容易犯的錯）、`watch` 要盯（今明兩天的事件與價位，附台北時間）、`flip` 會推翻（什麼收盤條件會讓框架動作，附價位與距離）。一律用框架語言（「依框架」「避險減 20%」），不寫任何人的持倉狀態。
- `changes`（今天變了什麼）3–5 項，只寫相對上一期真正改變的事：價格與量、資金流、衍生品、鏈上、市場階段天數；`fig` 寫「昨天 → 今天」的數字。沒有變化的不列。各版另外指定要記一筆的情況（實現市值 30 日正負翻轉、短期持有者成本真的上穿真實市場均價）見下面。

- 賣壓累積與動能品質（`chips.stress`，2026-11-07 起，本站自製，只用每日收盤；取代 11/05 的短期壓力分數）：`r` 是賣壓累積（0–100，動能低於 0.45 時累加、高於時遞減、到 0.7 歸零），`s` 是動能品質（0–1，近 21 天報酬的 t 值換成 0–1），`state` 是 bottom（賣壓 100 且動能 < 0.3）／near／build／strong／calm。寫的時候用「賣壓累積到 92、動能 0.28，接近底部組合」這類讀值；底部組合的回測要照實引用次數（`f30`、`f90`、`ex`、`era`：短期常常還有一跌、熊市初期多次失靈），不要寫成高確定性的買點；動能高（`strong`）不是頂部訊號。不要寫成任何付費指標的名字。
- 隱含波動率期限結構（`deriv.ivterm`，2026-11-08 起）：`t` 是 7／30／90／180 天的價平隱含波動，`slope` 是 7 天減 90 天（點），`state` 是 inv（≥ 1 點，近月較貴、倒掛）／flat／norm（≤ −1 點），`prev7` 是 7 天前那一條（11/14 起才有）。寫的時候用「7 天 38.4%、90 天 38.9%，曲線大致持平」這類讀值；倒掛只說市場覺得眼前風險較大，不要推論方向。
- 月度報酬（`price.monthly`，2026-11-08 起）：`mtd` 本月至今、`ytd` 今年至今、`cur` 是本月在 2013 年起的歷史（`n`、`up`、`med`、最好最差的年份）。只能寫成「過去 13 次 11 月上漲 8 次」這類歷史描述，不要寫成「11 月通常會漲」或任何預測；月初幾天的 `mtd` 意義不大，少用。

**flows（資金）**
- ETF：從 brief 的 `flows.etf` 讀數字；The Block 只公布已完整的交易日，最新完整日通常比 bar_date 晚一到兩個交易日，寫的時候標明日期。若最新完整日比 bar_date 落後超過 2 個交易日，在 flows 寫明「ETF 資料延遲」。暫定值的規則見步驟 4。
- 實現市值 30 日變化（brief 的 `flows.rc_liq`）：只當資金背景寫進 flows 判讀（例：「實現市值 30 日 +1.3%，資金仍在流入」）；轉為 ≤0 或由 ≤0 轉正時在 changes 記一筆。不得寫成加倉或賣出訊號，也不連動市場階段與出場框架（歷史上 2018、2021-06、2022-01 的歸零之後仍大跌，見資金版說明）。
- 可引用穩定幣供給（`flows.stables`）、Coinbase 溢價（`flows.cb_premium`）、恐懼貪婪（`flows.fear_greed`）。Coinbase 溢價（2026-11-05 起）：`pct` 是每日值（和 TradingView 的 CB-BN basis 同一種算法），`avg7` 是 7 日平均；兩個都寫，7 日平均會落後幾天。`rows` 約 4 年、第三欄是 Coinbase 收盤。過去「7 日平均跌破 −0.15%」只有 4 次（2022/11、2024/12、2026/06、2026/10），前 3 次 30 天後都上漲，但樣本只有 3 次；「收斂回 0 以上」本身沒有額外資訊（5 次 3 次上漲，和隨便一天差不多），不要寫成看多訊號。網站上的「即時」值是讀者打開網頁時瀏覽器自己抓的，日報不引用。

**onchain（鏈上）**
- 頂部三指標（MVRV Z／NUPL／Puell）由 CoinMetrics 自算，資料日期通常是收盤前一天，照實寫該日期（不要寫成 bitcoin-data 那種晚約 6 天的舊日期）。
- 可引用算力帶（`onchain.hash_ribbons`）。
- 短期持有者認賠賣壓（STH-SOPR）：brief 的 `chips.sopr_read` 有最新值與最近三次認賠低點（`kind`：easing＝價格回到前次認賠低點附近但深度較淺、賣壓遞減；heavier＝較深、賣壓加重）。可引用，但要寫明資料日期（來自 CheckOnChain，晚約 1 天、日線；盤中集中認賠會被當天的獲利賣出平均掉，日線不一定跌破 1），只作讀值、不寫成買點或見底預測。
- 每日淨實現損益：brief 的 `onchain.npl`（CoinMetrics 實現市值日變化 − 新發行，晚約 1 天；`usd_m` 當日淨值百萬美元、`rank_1y` 在之前 365 天的百分位、`sum7_usd_m`／`sum7_prev_usd_m` 近 7 日與前 7 日合計、`loss_spike_last`／`profit_spike_last` 最近一次 ≤2／≥98 百分位）。可寫「獲利了結降溫／增溫」「出現明顯認賠」並附數字與日期；只有淨值，不寫成獲利或認賠的總額。**不把認賠高峰寫成買點或見底，不把獲利高峰寫成頂部**。
  - 單日高峰（2026-10-18 即時可行回測，2015 起、每串高峰取第一天）：認賠高峰之後 30／90 日與平常沒有差別；獲利高峰之後 30 日中位 +12.9%（平常 +3.2%），但一輪比一輪弱（+21.5%→+12.3%→+5.0%），只能當趨勢強的佐證。
  - 30 日累計模式（`onchain.npl.cum30`：`pct_4y` 4 年百分位、`thr_pct_mcap` 觸發線、`trig` 歷次首次跌破、`trig_old` 舊規則的觸發、`green_max` 觸發線用的 4 年最大獲利、`min_since_top` 本輪最深）：2026-11-04 起觸發線＝之前 4 年最大 30 日淨獲利 × −1/4（舊規則是 4 年第 3 百分位，本輪沒觸發）。首次跌破：2015/01、2018/11、2020/03、2022/05、2022/11、2026/02、2026/06；2023 年以前 5 次有 4 次 1 年後上漲，2018/11、2022/05 之後還再跌 26%、46%。新規則是看過本輪結果才定的，只能寫成「週期級別的認賠／底部區佐證」，不寫成買點。ETF 時代這個訊號可能變鈍（ETF 股份在股市換手不上鏈、只有淨贖回才移動鏈上的幣；本輪最深認賠只有同輪最大獲利的 3–4 成，前兩輪約 7 成），寫到它時要附這個限制。
- 長短期持有者籌碼（`chips.cohort`，2026-10-27 起，`pipeline/cohort_urpd.py`）：**「現在」與「變化」來源不同**（2026-10-28 起）。`src`＝`checkonchain` 時，`rows`／`tot`／`loss`（現在的分布）來自 CheckOnChain 依每顆幣實際幣齡算的公開圖表（Bitcoin Research Kit，資料日 `now_date`，已套用搬家修正），不是推算；`src`＝`model` 表示 CheckOnChain 當天沒取到、退回推算。`model_rows`／`model_tot`、`cmp`、`flow` 一律是推算（bitcoin-data URPD × 幣齡分布 × 每日價格區間），`vs` 是推算和實際的差距（`sth_diff_pct` 總量、`misplaced_pct` 分錯格的比例）。`tot` 總量與平均成本；`rows` 每 2,000 美元一格的［價位, STH, LTH］（brief 略去，看 `chips.cohort_read` 的最厚格子）；`flow` 和約 30 天前比（`sth_spent`／`lth_spent` 那時的短期／長期持有者動了多少、`new` 之後買進還沒動的、`model_free_above` 價格沒碰過的高位區，變化就是賣出、不靠模型）；`loss` 收盤跌到各價位時帳面虧損的 STH／LTH；`val` 推算的 STH 成本 vs bitcoin-data 公布值。寫法：現在的分布在 `src`＝`checkonchain` 時寫「CheckOnChain，資料日」，不寫推算；變化（`flow`、`cmp`）一律標「推算」，可引用 `vs` 或 `val` 的差距；逐筆 UTXO、不是實體調整，交易所整理錢包會被算成換手，換手量偏高，不和 Glassnode／Murphy 的數字比大小；帳面虧損不等於會賣，要配合 STH-SOPR 與實現虧損寫；URPD 本身晚 1–2 天，寫明 `chips.cohort.date`。
  - **搬家日**（`chips.cohort.transfers`、signal `jump:urpd-transfer`，2026-10-27 起）：某天遠離現價的格子大量流出、同一天等量出現在現價那一格，逐筆 UTXO 會把它算成賣出再買進，但量大又集中的多半是同一實體整併錢包。模型已把這批幣放回原本的成本與幣齡（`raw` 是不修正的原樣）。寫法：這幾天的流出**不寫成賣出或低點買家離場**，寫「疑似內部轉帳」；同一天的淨實現獲利、STH-SOPR、短期持有者實現獲利高峰也是逐筆 UTXO 算的，會被同一筆搬家灌大，不能拿來佐證有人在賣。教訓（2026-10-22）：62–66K 一天少 19 萬顆、全進 80–82K，本站當時寫成「低點買家在賣」；Murphy 與 @market_beggar 指出 Glassnode 實體調整的 STH 已實現利潤當天沒有反應，是機構內部調倉。
- 價格 × 長期持有者動向（`onchain.lth_color`，2026-10-29 起，`pipeline/stage_viz.py` 的 `lth_color_viz`）：鏈上版的價格線依長期持有者 30 日淨部位上色（紅＝淨減、灰＝持平 ±5 萬顆內、藍＝淨增，±40 萬顆最深），資料就是 bitcoin-data `lth-net-position-change-30d`，不另打 API。`run` 是這段方向（只看正負）從 `start` 起連續 `days` 天、期間最深 `extreme`、同期價格 `price0`→`price`（`price_chg_pct`）；`prev_same` 是這段之前上一次一樣深的日子；`pct_4y` 四年百分位；`vs_hi1y_pct` 距一年高點。寫法：重點是**方向和價格的組合**——價格漲、長期持有者淨減＝趁反彈出貨，上方有供給；價格跌、長期持有者淨增＝持有者不賣；價格跌、長期持有者也減＝賣壓來自老幣。`run.days` 很短（例如 ≤ 7）代表剛翻方向，值得當發現寫。不可寫成「吸籌評分」或和 Glassnode 的 Accumulation Trend Score 比較：那個以實體計、排除交易所，是不同指標；bitcoin-data 同名的 `accumulation-trend-score` 是這條線的換算。淨增也包括幣放滿 155 天自動轉成長期持有者，不寫成「有人在買」。
- 長短期持有者供給比（`onchain.lsr`，2026-11-05 起，資料 Bitview `lth_supply`／`sth_supply`，`stage_viz.lsr_viz`）：`value` 現值、`d30`／`chg30_pct` 30 天前與變化、`d365` 一年前、`hi1y`／`lo1y` 一年內高低、`pct` 2015 起百分位。和 LTH 30 日淨部位是同一件事的比例版，寫在同一段；上升也包括幣放滿 155 天自動轉成長期，不全是買入。
- 賣方衰竭常數（`onchain.sec`，2026-11-02 起，資料 CheckOnChain，`coc.get_sec`／`stage_viz.sec_viz`）：獲利供給比例 × 30 天價格波動（Checkmate 設計），越低＝價格越平靜、虧損的人越多。`value` 現值、`pct` 2011 年起百分位、`th` 極端區門檻（0.13，本身歷史最低約 1%）、`hits` 歷次跌破（隔 90 天以上算新的一次；`low` 之後 90 天內最低、`r90`／`r180`／`r365` 之後漲跌、`dd365` 一年內最大回撤、`done` 是否滿一年）、`recent_low` 近 30 天低點。寫法：**刻度和 Glassnode 版不同，不寫「跌破 0.01」**，也不和 Murphy 圖上的數字比大小；可寫「近 30 天低點比上次跌破後的最低高（較高的低點）」這類形狀比較，標明只是形狀；歷次統計必須同時寫出回撤（2018/11 跌破後先跌 50%、2023/8 先跌 14%）與樣本少，不寫成買進訊號或「底部確認」。跌破 0.13（`value` < `th`）或近 30 天出現新低點時當成發現寫。
- 實現獲利 ÷ 實現虧損（`onchain.rpl`，2026-11-02 起，資料 CheckOnChain，`coc.get_rpl`／`stage_viz.rpl_viz`）：全網每日比值取 90 天平均；低於 1＝賣出的人整體在認賠（紅色）。`value` 90 天平均、`above`／`since`／`since_days` 目前在 1 的哪一邊與從哪天起、`first2` 這次第一次超過 2、`last7` 最近 7 天每日比值平均、`daily` 最近 14 天每日值、`proj` 每日比值維持 `last7` 時 90 天平均哪天跨過 1（試算）、`reds` 歷次低於 1 的期間（`major` 60 天以上、`relapse` 結束後一年內又跌回的期間）。寫法：90 天平均反應慢，**先看 `last7`**；`last7` < 1 連續出現或 `proj` 有日期時當發現寫；不寫「牛市確認」或「不會再回到紅色」，必須同時提 2019/12–2020/1 的例外（回到 1 以上 7 個月後又跌回 37 天）。
- 表觀需求（`onchain.ad`，2026-11-03 起，資料 CheckOnChain HODL Waves，`coc.get_hodl1y`／`stage_viz.ad_viz`）：CryptoQuant 的定義，30 天新挖出的幣 − 30 天內 1 年以上未動供給的變化；`value` 30 天合計、`sma30` 它的 30 日平均、`inact_chg30` 1 年以上供給 30 天變化、`moves` 疑似搬家日（單日 1 年以上供給掉超過 `move_thr`，`echo` 一年後的回音日、`echo_rise` 回音當時實際增加多少）、`echo_soon` 60 天內會到的回音。寫法：負值要同時說明「一年前換手的幣滿一年」的機械效果，不單獨寫成需求崩潰；`value` 跌破 `sma30` 才寫「需求轉弱」；回音日前後（例如 2026-11-22）的大幅下跌寫「疑似搬家的回音」，不當發現；逐筆 UTXO、不是實體調整，不和 CryptoQuant 的數值比大小。
  - 1 年版（`onchain.ad.y1`，2026-11-05 起）：同樣算法的 365 天合計（`value`、`issued`、`inact_chg`、`pct` 2020 起百分位）。`combo` 是 2016 年起「30 天負、1 年正」的天數與之後 90 天上漲比例／中位數，對照所有日子（`all_up90_pct`／`all_med90`）。這個組合常被說成牛市中的回調，但資料上之後 90 天表現比平均差，不要寫成看多訊號。
- 長期持有者虧損比例（`onchain.lthloss`，2026-11-04 起，資料 CheckOnChain，`coc.get_lthloss`／`stage_viz.lthloss_viz`）：持有 ≥155 天的幣裡帳面虧損的比例。`peaks` 歷輪熊市底部的高點（`after_max` 高點後 90–730 天內的最高，用來驗證「脫離底部後不再創新高」）、`post_min` 這輪高點後的最低、`cohort.break_price` 用 CheckOnChain 長期持有者籌碼推算「虧損比例超過這輪高點」的價格（每天重算）。寫法：價格接近或跌破 `break_price` 時當發現寫（等於打破規律）；回升時可以寫「指標回調、測試支撐」，但要同時寫明樣本只有 3–4 輪、2020/3 是先暴跌才回升；比例上升也可能來自高價買進的短期持有者滿 155 天轉成長期持有者，不全是價格造成。
- 長期持有者已實現虧損（`onchain.lthrl`，2026-11-05 起，資料 Bitview `lth_realized_loss_sum_24h`，`stage_viz.lthrl_viz`；不是 Glassnode 的實體調整版）：7 日合計 ÷ 市值（`rel`，%）與美元（`usd7_m`，百萬），`pct` 2015 起百分位；`lows_now` 本輪（最近一次週期頂部之後）各擺動低點前後 7 天的最大值；`bears` 歷輪熊市的低點與最大的一次（`last_is_max`）。寫法：照實寫本輪各低點的大小；歷史上前三次熊市都是底部那次虧損最大，所以**不要**把「價格新低但虧損變小」寫成賣壓衰竭或底部訊號。
- 短期持有者成本帶（`onchain.sth_bands`，2026-11-04 起，資料 Bitview，`bitview.get`／`stage_viz.sth_bands_viz`；Murphy 的「短期持有者成本基礎模型」）：帶＝短期持有者成本 ×（近 4 年「價格 ÷ 成本」的平均 ± 1、2 個標準差）。`now.z` 是收盤在第幾個標準差，`now.bands` 是六條帶的價位（2026-11-05 起多了 `0.5`、`-0.5`，離現價最近的上下兩條），`stats` 有近 4 年在 ±1 標準差外的天數比例和最近一次。寫法：只寫位置和帶的價位（「收盤在 −0.2 個標準差，+1 標準差 88,869」），不寫「會回踩到哪」；碰到 +1 標準差或跌破 −1 標準差時可以當發現寫。
- 6–12 與 12–18 個月持幣成本（`cycle.age_cost`，2026-11-04 起，資料 Bitview，`stage_viz.age_cost_viz`；wander 的成本線交叉）：`c612`、`c1218` 兩條線，`crosses` 歷次死叉／金叉與間隔天數，`last_cross`、`days_since`。兩條線是半年到一年半前的平均買價，非常落後；真的交叉時在 changes 記一筆，平常不必寫。
- RV30 一年分位（`price.vol.rv30_pct1y`、`rv30_min1y`、`rv30_min1y_date`，2026-11-04 起，Kraken）：第 10 百分位以下時可以寫「低波動之後常有大波動」，一定要接「方向不一定」。
- 近一年位置（`price.q365`：`pct`＝收盤在近 365 根日線收盤裡的百分位，`q10`／`q25`／`q50`／`q75`／`q90` 分位線，2026-11-09 起，Kraken）：只用價格算，和 Mayer 倍數是同一件事，不要寫成另一個獨立訊號。跌破 `q10` 的期間，前三輪的週期低點都落在裡面，但每段持續 3–7 個月，第一次跌進去後一年內還再跌 35%–52%，不能寫成見底或買點。
- 資料來源（2026-11-04 起）：鏈上指標表的長短期持有者成本、aSOPR、LTH-SOPR 改用 Bitview（`onchain.metrics.*.source`，晚 1 天），數字和以前的 bitcoin-data 版略有不同，寫日期時用資料本身的 `date`。長短期持有者籌碼的 `chips.cohort.cmp.src`＝`bitview` 時「30 天前」是實際值（`cmp_model` 是舊的推算），可以寫「實際」；`flow`（誰賣了、誰轉成長期）仍是推算。
- 鯨魚分層（`onchain.whales`，2026-11-04 起 Bitview，`src`）：依地址餘額分層，地址不等於實體；交易所大量提幣時幣從大地址分散到小地址，看起來像大戶賣、散戶買，寫之前先看同期 ETF 流量與交易所供給。
- 3–6 個月持幣成本（`cycle.age_cost.c36`）：`since` 是價格上穿至今的天數，`ups` 是歷次上穿（`bear`＝熊市後第一次）。不寫「上穿後約 80 天到頂」這類倒數：只有 2019 年吻合。
- 1 週–1 個月持幣成本（`cycle.age_cost.c1m`，2026-11-05 起，Bitview `age_1w_to_1m_realized_price`）：最近一個月進場、還沒動的短期持有者平均成本。`gap_pct` 收盤距離、`since`／`days` 這次在線上／線下從哪天起連續幾天、`chg30` 30 天變化、`vs_sth_pct` 比短期持有者成本高多少。寫法：只寫位置和距離，不說「守住就延續」。
- Hyperliquid 大戶（`deriv.hl_whales`）：帳戶淨值前 2,000 名（2026-11-05 起，原 300 名）的 BTC 部位彙總（實際部位）；只有 Hyperliquid，大帳戶可能是做市或避險，不寫成「大戶看空」。不寫個別帳戶，也不要從別處補個別帳戶的部位。`bands.rows` 是清算價在收盤 ±25% 內、每 1,000 美元一格、至少 5 個帳戶且最大一個不超過一半的價位（網站在清算熱力圖右緣畫白條）；空的時候代表大戶清算價分散、沒有聚集，照實寫「沒有聚集」，不要改用更寬的格子去湊。`bands.hidden.long／short` 是不畫的部分按多空的合計（帳戶太少時只有帳戶數）。
- 成本線與均線（`cycle.levels`，2026-11-04 起）：`levels` 各條線的價位與離收盤的距離，`near` 收盤下方 8% 內擠在一起的線。寫法：列位置與距離，不寫「守住就延續、跌破就整理」這類條件預測。
  - 活躍投資人成本（`cycle.levels.act`，2026-11-05 起，Bitview `active_price`，Cointime 的 Active Price）：依幣的活躍程度加權的平均成本，也在 `levels` 裡（key `act`）。`ytd_above`／`ytd_days` 今年收在它上方的天數、`last_above` 最近一次收在上方、`last_cross` 最近一次穿越。可以寫「今年 308 天只有 35 天收在它上方」這種事實，不寫成壓力位預測。
- 和前幾輪比（`cycle.cycle_cmp`，2026-11-05 起，統一收盤＋model.json 的週期頂部）：各輪頂部之後每天收盤 ÷ 頂部收盤。`day_now` 今天是這輪頂部後第幾天；`cycles[].at` 各輪同一天的位置、`low` 頂部後最低（第幾天、跌幅）、`back_day`／`back_after_low` 重新收上頂部價花的天數。寫法：可以比較「同一天前幾輪在哪裡」，但只有三輪樣本，不推論這輪的時間表。
- BTC 對美股（`flows.btc_vs_stocks`）：`win90` 近 90 個美股交易日勝率、`excess90` 每日平均超額（百分點）、`rel.last` 近兩個月各資產漲跌（黃金是 PAXG）。BTC 與美股收盤差約 3 小時。
- 選擇權：`deriv.viz.options.strikes2` 是未平倉第二大的到期，`totals` 是全部到期的買權／賣權（顆、十億美元）；未平倉不分買方賣方，買權多不等於大家看漲。
- 短期持有者獲利比例（`chips.flow.sth_in_profit_pct`）2026-11-04 起是 Bitview（`source`），和以前的 bitcoin-data 版差幾個百分點；97.5% 以上是常見的「賣出線」。清算熱力圖 `deriv.liq_heat.far` 是畫面外 ±25% 內最亮的一塊。
